# 资产合集流水线:机制与取舍

> 本文解释本合集为什么这样构建、边界划在哪里、哪些做法被否决。执行依据是 `scripts/` 的实际行为与 `schemas/` 的 JSON Schema,本文不重复字段表,也不写操作步骤。

## 一、合集在资产生态里的位置

资产是纯数据,由用户导入到 dsc-humanize 侧使用;包格式、Schema、骨架与校验脚本只在 [dsc-humanize-asset-template](https://github.com/omds-chat/dsc-humanize-asset-template) 维护。资产生态里有两级证书,没有中间 CA:

| 层级 | 证书 | 签发者 | 本仓库持有的部分 |
|:---:|:---:|:---:|:---:|
| 第一级:根 CA | `certs/dsc-humanize/dsc-humanize-root-ca.crt` | 自签 | 只有根证书与配对公钥,根私钥不入库 |
| 第二级:合集 EEC | `certs/awesome-dsc-humanize-asset/awesome-dsc-humanize-asset-eec.crt` | 根 CA | 证书与配对公钥;EEC 私钥只在 CI secret |

本合集是资产生态里的一个来源,做三件事:登记作者与包、按登记拉取并分发、用 EEC 给分发内容的三层摘要签名。它不做第四件事——不改写包、不替作者背书内容、不对资产包本身做代码签名。

资产包不做代码签名是格式层面的结论,不是本合集的取舍:包是可导入的纯数据,包里也不允许出现签名材料。因此本合集能提供的完整性只有一种:清单记录「这次分发的字节是什么」,签名证明「这份清单出自持有 EEC 的一方」。作者身份由登记与 PR 评审确认,不由签名确认。

## 二、catalog 驱动模型

`catalog/` 是唯一入口,只登记三件事:作者、作者站点基址、包标识。

| 登记项 | 为什么在这里 | 为什么不登记别的 |
|:---:|:---:|:---:|
| 作者目录与 `author.json` | 身份要能被评审看见,且是分发路径 `assets/<作者>/` 的目录名 | 不登记作者公钥:资产不做代码签名,收了也没有验证路径 |
| 包目录与 `package.json` | 包标识是分发路径 `assets/<作者>/<包标识>/` 的目录名,也是索引键 | 不登记名称、说明、许可证、版本、类型:它们在包元数据里,重复登记必然分叉 |
| `base_url` | 版本与包内文件由作者站点提供,合集只认这个地址 | 不登记版本目录:版本由站点发现,合集不预先裁剪作者发版 |

这条边界的代价是构建必须联网,收益是「包元数据只有一份」。若在登记里也写一遍 `name`、`license`,一次改名就要两处同时改,漏一处就出现两个互相矛盾的事实,而校验脚本只能判形状,判不出哪个是对的。

包标识在合集内唯一:同一个包的不同版本由 `version` 区分,不靠换 `id` 区分。原因是消费方的来源记录按 `id` 回答「取自哪个包」,换 id 等于换包。

## 三、拉取模型

作者站点按下面的约定发布,它与资产包格式是两件事:前两行是本合集的要求,其余是包本体。

```text
<base_url>versions.json        版本索引:latest、versions 与每个版本的包内文件列表
<base_url><版本>/<包内路径>     包内文件,按字节原样
```

`files` 是本合集对作者站点唯一的额外要求,理由只有一条:HTTP 无法列举目录。合集必须知道某个版本有哪些包内文件,否则既不能拉取,也不能在拉取后判断「包内该有的都在」。

它放在包外的索引里,而不是包内:

| 方案 | 结果 |
|:---:|:---:|
| `files.json` 放在版本目录里 | 版本目录就是包根,包根会多出一个规范之外的条目,包不再合规 |
| 让作者按固定文件名发布 | 文件名不承载语义,固定名等于把规范里「文件名可任意」作废 |
| 用 `versions.json` 的 `files` 字段 | 索引在包外,包根保持干净,且一次请求就拿到全部版本的文件列表 |

代价是索引与包内容可能对不上:作者改了包却忘了更新 `files`。这一条由构建侧兜住——`asset.json` 的 `types` 与 `files` 里出现的类型目录双向比对,任何一边多了少了都判该包不合规并剔除,不会带着残缺的包发布。

不从 GitHub Release 取任何东西:Release 没有版本索引的语义,也要求消费方按 tag 猜路径;站点索引是作者自己维护的一份明确声明。

## 四、三层清单与 revision

发布目录按「作者 / 包 / 版本」三层组织,每层一份 `manifest.json` 与 `manifest.json.sig`:

| 层 | 位置 | 覆盖的文件(相对该层目录) |
|:---:|:---:|:---:|
| L1 | 发布目录根 | `meta.json`、`assets.json`、`tags.json`、`assets/author_manifest.json` |
| L2 | `assets/<作者>/` | `asset_manifest.json` |
| L3 | `assets/<作者>/<包标识>/` | `versions.json`、各版本目录下的全部包内文件 |

三条约定:

- `catalog/` 与 `certs/` 不进任何清单:前者是登记信息,后者是信任材料。把它们纳入清单会让一次登记改动牵动全部摘要,也会让证书材料变成清单的一部分。
- 清单只记路径与 SHA-512,不记版本号与作者名。层与层之间互不引用,所以任何一层都可以单独校验、单独重签。
- L3 覆盖到包内每个文件,不覆盖 `manifest.json` 与其签名。这是「资产不做代码签名」在分发侧的落点:包的每一个字节都由 L3 清单绑定,没有单独的文件签名。

`revision` 每层独立:该层文件集合与哈希都没变时沿用旧值,有变化时加一,没有旧清单时从 1 开始。值从已发布站点的同名 `manifest.json` 读取——发布目录是构建产物,不入库,源码树里没有可沿用的旧值。

层间不做收束:如果收束成一份根清单,任何一个包发版都会改动根清单,所有消费方都得重拉整份摘要;分层之后,改一个包只让 L2 与 L3 的 revision 加一,L1 不变。

## 五、证书与签名边界

三个角色,谁签什么一目了然:

| 角色 | 承担者 | 持有物 | 签发对象 |
|:---:|:---:|:---:|:---:|
| 根 CA | dsc-humanize(资产侧自签根) | 根私钥(离线,不入库)、根证书 | 本合集的 EEC |
| 终端签名方(EEC) | 本仓库 | EEC 私钥(CI secret)、EEC 证书 | 三层清单的 CMS 分离签名 |
| 资产作者 | 外部作者 | 无密钥要求 | 不签任何东西 |

已定约束:

| 约束 | 内容 | 理由 |
|:---:|:---:|:---:|
| 只对清单签名 | 签名对象是三层 `manifest.json`,不是 `asset.json` 或内容文件 | 资产是纯数据,格式不允许包里出现签名材料;清单已经绑定全部包内字节 |
| 脚本不实现签名 | `scripts/` 只生成清单;CMS 签名与独立验签都由 CI 的 `openssl` 命令完成 | 签名语义只允许一个实现,脚本接管就会与 `openssl` 分叉 |
| 签名失败即失败 | 任一清单签名失败,构建以非零退出码中止 | 清单是分发的完整性凭据,缺签名的发布没有意义 |
| 证书只由上游签发 | 本仓库不生成、不签发、不替换任何证书,只原样收录公开材料 | 签发权在根 CA 一方;仓库里出现签发动作,等于把信任锚的所有权弄乱 |
| 私钥不入库 | EEC 私钥只在 CI secret,根私钥永不进入本仓库 | 私钥入库等于把签发能力交给所有能读仓库的人 |

签名参数固定为 `openssl cms -sign -binary -md sha512 -outform DER -nocerts -noattr`,验签带 `-inform DER`。`-binary` 保证按原始字节处理,不经换行规范化;`-md sha512` 显式给出,不依赖默认值漂移;DER 是跨仓库统一格式,消费方在浏览器里解析 CMS 时只认它。

分发出去之后的校验是弱校验:清单签名、证书链、包内容与清单不一致都只警告,由用户决定是否继续。分发之前的校验是强校验:任何一项不通过都不发布。

## 六、异常剔除

构建把「作者要改的东西」与「运行时偶然失败」分开:

| 类别 | 判定 | 构建行为 |
|:---:|:---:|:---:|
| 登记不合规 | 登记文件本身不合法:缺字段、`id` 与目录不符、`base_url` 不合规、标签越界、缺 EEC 证书 | 中止,一个包都不发布 |
| 运行期异常 | 站点不可达、`versions.json` 不合规、包根出现规范之外的条目、`asset.json` 字段或取值不合规、类型声明与内容不一致 | 只剔除该包,其余照常发布;写入 `catalog/anomalies.json` |
| 分发自身故障 | 清单生成失败、清单签名失败、发布目录自检失败 | 中止,不发布半成品 |

界线的判据是「谁该改」:登记写错了,只有作者能改,发布一个没有该包的合集只会让目录与分布对不上;站点临时不可达,作者不需要改任何东西,剔除是临时的,下次构建自动回归。分发自身故障既不是作者的问题,也不能靠剔除绕过,只能中止。

剔除不等于解除登记:包目录仍留在 `catalog/` 里。真要下架,删目录并在 `removed.json` 留记录。

## 七、与插件合集的差异

两个合集共用同一套「目录登记 + CI 拉取 + 用合集证书重新签名」的骨架,但收录对象不同,取舍随之不同。

| 维度 | 插件合集(awesome-dsc-plugin) | 本合集 |
|:---:|:---:|:---:|
| 收录对象 | 可执行插件,单文件 ESM | 纯数据资产包 |
| 作者公钥 | 必收,用于校验作者自签名 | 不收,资产不做代码签名 |
| 产物签名 | `plugin.js.sig`,逐版本 | 无,包内不放签名材料 |
| 清单覆盖 | 三层清单,覆盖元数据与作者公钥 | 三层清单,覆盖到包内每个文件 |
| 版本索引 | `versions.json`,只有 `latest` 与 `versions` | 同上;作者站点侧另有 `files` 字段供拉取 |
| 信任锚 | ds-chat 根证书 | 资产根证书,两条链互不隶属 |
| 登记字段 | 名称、说明、许可证、仓库、站点、标签 | 包标识、站点、仓库、标签 |

少收的东西比多收的多:没有作者签名,就没有「公钥与签名两侧不齐」这类判定;没有可执行产物,就没有引擎版本与能力申请;资产不进入宿主加载路径,回收与停用都发生在用户侧。

## 八、已否决的做法

| 做法 | 理由 |
|:---:|:---:|
| 在本仓库另存一份资产包规范与 Schema | 同一份契约两处维护,分叉后无法判断哪一份权威;规范只有 template 一个源头 |
| 提供 `awesome-dsc-humanize-asset-set-template` 这类「复刻自身」的模板仓库 | 模板与合集必须逐项同步,同步漏一处就产出结构合法的错误合集;需要新合集时直接按本仓库结构做 |
| 给资产包加作者签名 | 格式禁止包内出现签名材料;加了也没有验证路径,反而让人以为作者背书了内容 |
| 用插件合集的根证书验资产来源 | 两个信任域互不隶属,借用一边的结论会把「插件被认可」误当成「资产来源被认可」 |
| 把根证书随发布目录下发 | 锚随内容走,校验方读到的根就可能与本地锚不同,信任结论变成由分发方决定 |
| 聚合索引替代逐层取件 | 聚合索引不进任何清单、不参与验签;一旦与清单不一致,消费方拿不到可用于校验的摘要 |
| 版本留在 catalog 里登记 | 版本会随作者发版频繁变化,登记目录变成版本清单,PR 评审被版本号噪声占满 |
| 用 `files.json` 放进包根 | 包根只允许元数据、类型目录与可选说明,多一个文件即不合规 |
| 按固定文件名发布包内内容 | 规范明确文件名不承载语义,固定名等于作废这条约定 |

## 九、未定稿项

这些项不影响当前实现的自洽性,但会在契约变化时回来重定,先记在这里避免重复论证。

| 项 | 现状 | 待定的原因 |
|:---:|:---:|:---:|
| 消费方取件顺序 | 本文给出 `assets.json` 与三层清单的路径契约 | 资产导入由内核与插件实现,导入通道未定稿前无法固定消费顺序 |
| 下载计数 | 未启用,合集元数据只有两个版本字段 | 资产由用户导入,「下载」缺少统一定义,计数的触发点取决于导入实现 |
| 展示站点 | 不提供,发布目录只有索引、清单、信任材料与包 | 资产浏览与导入界面落在宿主侧,站点重复一套只会分叉 |
| 资产包的撤回 | 只提供 `removed.json` 记录与全量重建 | 已导入到用户侧的包如何得知上游变化,取决于内核与宿主的更新通道 |
| 摘要之外的元数据清单 | 清单只记路径与 SHA-512 | 是否需要在清单里附带版本与作者,取决于消费方是否需要免请求的展示数据 |
